# Supabase setup

My-nutritionist works without any backend: with no Supabase configuration it runs in **Offline/Local mode**
(guest data in IndexedDB on the device). Connect a Supabase project to get accounts, sync across devices and
USDA FoodData Central search.

What lives in `supabase/`:

| Path | Purpose |
|---|---|
| `migrations/001_initial_schema.sql` | Tables, CHECK constraints, stale-write trigger (canonical schema) |
| `migrations/002_rls_policies.sql` | Data API grants + Row Level Security policies for every table |
| `migrations/003_seed_foods.sql` | The 70 USDA-sourced system foods (generated by `npm run seed:sql`, do not edit) |
| `seed.sql` | Intentionally empty: reference data ships as migration 003, user data is never seeded |
| `functions/food-search/` | Edge Function proxying USDA FoodData Central (contract: `docs/contracts/food-search-function.md`) |
| `tests/database/*.test.sql` | pgTAP tests: RLS enabled, exact policies, exact grants, RLS behaviour |
| `config.toml` | Local stack configuration (also read by `supabase functions deploy`) |

## 1. Which values are safe where

| Value | Where it may live | Notes |
|---|---|---|
| Project URL (`https://<ref>.supabase.co`) | Browser (`VITE_SUPABASE_URL`) | Public |
| Publishable key (`sb_publishable_…`) | Browser (`VITE_SUPABASE_PUBLISHABLE_KEY`) | Designed to be public; RLS protects the data |
| Legacy `anon` JWT | Browser (`VITE_SUPABASE_ANON_KEY`), older projects only | Same exposure model as the publishable key |
| Secret key (`sb_secret_…`) / legacy `service_role` JWT | **Never in the browser or the repo.** Server code and local test tooling only | Bypasses RLS. `src/lib/env.ts` refuses it and falls back to Offline/Local mode |
| `FDC_API_KEY` (api.data.gov key) | **Edge Function secret only** | Keys found in public code are deactivated by api.data.gov |
| Database password | Password manager; typed into `supabase link` | Never in env files of the app |

Every `VITE_*` variable is inlined into the public JavaScript bundle at build time. Only the project URL and the
publishable (or legacy anon) key may ever be put there.

## 2. Behaviour without credentials

- `VITE_SUPABASE_URL` or the key missing → **Offline/Local mode**: no crash, no network calls to Supabase, all data
  stays on the device, Profile shows "Running in Offline/Local Mode". USDA search is unavailable (it needs an account);
  the bundled catalog and Open Food Facts still work.
- A malformed URL or a secret/service-role key → the app logs why, ignores the configuration and stays in Offline/Local mode.
- "Connected to Supabase" is shown only after a request to the project actually succeeded.

## 3. Local development (Docker)

Requires Docker. The Supabase CLI is a dev dependency (`npx supabase …`).

```bash
npm run db:start                 # supabase start: Postgres, Auth, PostgREST, Edge Runtime, Mailpit (emails)
npx supabase status -o env       # prints API_URL, PUBLISHABLE_KEY, SECRET_KEY, … for the local stack
```

Create `.env.local` (gitignored) from `.env.example`:

```bash
VITE_SUPABASE_URL=http://127.0.0.1:54321          # API_URL
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…    # PUBLISHABLE_KEY
```

- `npm run db:reset` re-creates the local database from `migrations/` (then runs the empty `seed.sql`).
- Confirmation and password-reset emails are caught by Mailpit at http://127.0.0.1:54324 (local sign-ups are
  auto-confirmed: `[auth.email] enable_confirmations = false`).
- `npm run db:types` regenerates `src/lib/database.types.ts` from the local schema after a migration change.

### Edge Function locally

Create `supabase/functions/.env` (gitignored, local only):

```bash
FDC_API_KEY=DEMO_KEY
```

`DEMO_KEY` works for smoke tests only (api.data.gov currently allows it about 10 requests per hour). Get a free
personal key at https://fdc.nal.usda.gov/api-key-signup for regular development and put it in the same file.

```bash
npx supabase functions serve food-search   # loads supabase/functions/.env, reloads on edits, prints logs
# → http://127.0.0.1:54321/functions/v1/food-search
```

Expected answers (the function contract is `docs/contracts/food-search-function.md`): no signed-in user →
`401 unauthorized`; an invalid body (e.g. a 1-character query) → `400 invalid_request`; a signed-in user's search →
`200` with normalized foods. The function's own logic is unit-tested without network by `npm run test:db`
(project `edge-functions`).

## 4. Hosted project

### 4.1 Create the project and find the values
1. https://supabase.com/dashboard → **New project**. Pick a region close to your users and save the generated
   database password in a password manager.
2. **Project URL and publishable key**: both are shown in the project's **Connect** dialog (button at the top of
   the dashboard). The URL is `https://<project-ref>.supabase.co` (also under **Project Settings → Data API**).
   The publishable key (`sb_publishable_…`) is listed under **Project Settings → API Keys**; if the project has none
   yet, create one there. Older projects show the legacy `anon` / `service_role` keys on the "Legacy API Keys" tab.
3. Put them in `.env.local` (development) or your host's build environment (production):
   ```bash
   VITE_SUPABASE_URL=https://<project-ref>.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
   ```

### 4.2 Apply the database migrations
```bash
npx supabase login
npx supabase link --project-ref <project-ref>     # asks for the database password
npx supabase db push --dry-run                    # lists 001, 002, 003
npx supabase db push
```
Without the CLI: open **SQL Editor** and run `001_initial_schema.sql`, `002_rls_policies.sql` and
`003_seed_foods.sql` **in this order**, each as one script. Never change tables by hand; add a new migration instead.

**Seed data**: the system food catalog is migration 003, so `db push` installs it; do not use `--include-seed`
(the seed file is empty by design). Check in the SQL Editor:
`select count(*) from public.food_items where created_by is null;` → `70`.

### 4.3 Auth settings
- **Authentication → Sign In / Providers → Email**: enabled. Keep **Confirm email** on in production: new users
  confirm their address from the email before their first sign-in.
- **Authentication → URL Configuration**:
  - **Site URL**: your production origin, e.g. `https://nutrition.example.com`. It is the default target of
    confirmation and password-reset links.
  - **Redirect URLs**: the production origin (exact), plus `http://localhost:5173/**` for development and your
    host's preview-URL pattern if you use preview deployments. Password-reset links only return to allowed URLs.
  - The browser client uses the PKCE flow (`src/lib/supabase.ts`), so a confirmation or reset link must be opened in
    the same browser that requested it.
- **Emails**: the built-in email service only delivers to members of your Supabase organization and is strongly
  rate limited. Configure **Authentication → Emails → SMTP Settings** with your own provider before inviting real users.

### 4.4 Deploy the Edge Function
```bash
npx supabase secrets set FDC_API_KEY=<your api.data.gov key>
npx supabase functions deploy food-search
npx supabase secrets list                        # FDC_API_KEY listed (value shown only as a digest)
```
`deploy` reads `[functions.food-search]` from `config.toml`: `verify_jwt = false` because the platform check also
admits publishable/secret API keys; the function itself verifies the caller's **user** session JWT
(supabase-js `auth.getClaims`) and answers `401 unauthorized` otherwise. Quick check:

```bash
curl -i -X POST https://<project-ref>.supabase.co/functions/v1/food-search \
  -H "apikey: sb_publishable_…" -H "Content-Type: application/json" \
  -d '{"action":"search","query":"oats"}'
# → 401 {"error":{"code":"unauthorized",…}}  (signed-in users get 200 through the app)
```
Without the secret the function answers `503 not_configured`; the app keeps working with the bundled catalog and
Open Food Facts, and USDA results are simply unavailable.

### 4.5 Run the app and test the connection
```bash
npm run dev            # http://localhost:5173
```
Sign up, sign in, then open **Profile**: it shows **"Connected to Supabase"** once a request to the project
succeeded, plus the number of changes waiting to sync. Log a meal on one device and sign in on another to see it synced.

## 5. Security tests

Grants and RLS are tested against the **local** stack (the tests refuse any non-local API URL):

```bash
npm run db:start
npm run test:db          # Vitest: RLS/grants/constraints through PostgREST + food-search unit tests
npx supabase test db     # pgTAP: supabase/tests/database/*.test.sql
# food-search unit tests only (no Docker needed):
npx vitest run --config vitest.db.config.ts --project edge-functions
```

`npm run test:db` reads the URL and keys from `supabase status -o env` at runtime (no key is stored in the repo),
creates two throwaway users with the Auth admin API, signs them in with a password and deletes them afterwards.
It covers: RLS enabled on every table; anon cannot read or write any user table but can read system foods; full CRUD
on own rows; no access to another user's rows (read, insert as, update, delete, upsert over, re-assign ownership);
system foods are read-only; favorites and meal logs can only reference visible foods; CHECK/UNIQUE constraints; the
stale-write guard; cascade delete of a user; and that the seeded catalog matches `src/data/system-foods.json`.

For a hosted project, run the database advisors after every migration:
`npx supabase db advisors --linked --type security` (or **Advisors → Security Advisor** in the dashboard).

### Security model in short
- **Grants** (who may touch a table at all): `anon` may only `SELECT food_items`; `authenticated` and
  `service_role` get `SELECT, INSERT, UPDATE, DELETE` on the eight tables; nobody gets `TRUNCATE`. New objects in
  `public` get no automatic API access — every future migration must `GRANT` explicitly.
- **RLS** (which rows): every policy uses `(select auth.uid())`. Users read and write only rows they own; UPDATE
  policies repeat the owner check in `WITH CHECK`, so ownership can never be re-assigned. System foods
  (`created_by is null`) are readable by everyone and writable by no client. A favorite or meal log may only
  reference a system food or one of the user's own foods.
- **Stale writes**: a trigger ignores an update whose `updated_at` is older than the stored row (offline sync safety).
- **Account deletion** cascades to every row the user owns.

## 6. Deployment basics
1. `npm run build` → static files in `dist/` (hash-based routing, so no server rewrite rules are needed).
2. Host `dist/` on any static host (Netlify, Vercel, Cloudflare Pages, GitHub Pages, S3 + CDN).
3. Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in the host's **build** environment — they are
   inlined at build time, so rebuild after changing them. Never add a secret key or `FDC_API_KEY` there.
4. Add the production origin to **Authentication → URL Configuration** (Site URL / Redirect URLs).
5. Deploy schema changes with `npx supabase db push` and function changes with `npx supabase functions deploy`.

## 7. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Profile keeps showing "Running in Offline/Local Mode" | `VITE_*` variables missing at build/dev-server start, or a secret key was supplied (refused) |
| `permission denied for table …` (code `42501`) on reads | Migration 002 not applied, or the request was made without a signed-in session |
| `new row violates row-level security policy` (`42501`) | Writing a row for another user, a system food, or referencing another user's food |
| `food-search` returns 401 | No signed-in user session (the publishable key alone is not enough) |
| `food-search` returns 503 `not_configured` | `FDC_API_KEY` secret not set (`npx supabase secrets set …`) |
| `food-search` returns 429 | The api.data.gov hourly quota is used up; wait for `Retry-After` |
| Password-reset link opens the wrong site | Redirect URL not in the allow list; the Site URL is used instead |
